## セーブ互換（`tools/compat-check.mjs`、旧版=公開中の Stage 38 `ef5e8c7`、新版=公開候補。同じ origin・同じ保存キー）
旧版が1800年開始のゲームを6年進めて保存（自動保存と手動スロット2）→ 新版が同じブラウザの保存を開く → 旧版が新版の書いた保存を開く。
- 合格（11/16）: 旧版の保存が**そのまま復元**（月・首都・路線199・都市101・人口が一致）、隔離やロックなし、続きを遊べて保存できる、手動スロット2はそのまま、再読み込みで新版の保存が戻る、ページエラーなし、旧版が新版の保存を開いても壊れない（読み込めた・上書きしない）。
- **この検査で見つけた不具合（修正済み）**: 1800年開始のゲームを保存して読み込むと、遷都の初回年 `relocFirst` が 1900 から 1950 に変わっていた。`save2.ts` の検証が「1950以上」と決め打ちで、1800年開始の正しい値 1900 を捨て、別の日程を作り直していたため。**現在公開中の版にも同じ不具合がある**（`ef5e8c7` の `save2.ts` に同じ行）。修正: 1800年開始のゲームでは 1900 以上を認める（`tests/unit/save2.test.ts` に追加）。修正後、この検査の「開始年と最初の遷都年が変わらない」が合格（1800/1900）。公開中の版で保存済みの 1800 年ゲームは、読み込み時に既に 1950 へ変わって保存し直されている可能性があり、その値は元に戻せない（新版は保存された値をそのまま使う）。
- 不合格5件は**この検査の前提が合わない項目**: 「旧版の保存が Stage 34 の記録を持たない」「旧い保存が Stage 34 の記録を作らない」「`:pre-s35` に原文が残る」「`:pre-s35` と一致」「巻き戻し後も `:pre-s35` が残る」。いずれも Stage 31〜35 への移行（旧版が Stage 34 より前）を検査する項目で、旧版が Stage 38 の今回は、旧版の保存が最初から Stage 34 の記録を持ち、`:pre-s35` は「より古い版の保存を上書きするとき」にしか作られない。保存キーは `s3:auto`・`s3:auto:prev`・`s3:slot2` が残っていることを確認した。
- 昇格都市の保存・読込・再進行の一致（人口・都市ID・路線・計画・乱数）は単体テストとE2E（手動保存スロット、再読み込み、読込）で確認済み。1950年開始と昇格しない旧セーブは昇格も定義も持たないことをテストで確認済み。
