# Stage 40 の残課題（調査結果と、独立Issueへ分離する作業）

## A. 鉄道重視の元号で1860年以降に鉄道延長が止まる（調査済み・未修正）
固定シード7・1800年開始・自動、年ごとの鉄道プロジェクトの状態と方針ダイヤル:
| 年 | 鉄道重視（正化相当） | 均衡 |
|---|---|---|
| 1840 | open 14, abolished 5 | open 7, building 7, abolished 7 |
| 1860 | open 26, building 1 | open 52, building 5 |
| 1880 | open 20 | open 44, building 4 |
| 1900 | open 8, building 1 | open 25, building 1 |
| `railBuild`（1840/1860/1880/1890/1900） | 1.00 / 0.67 / 0.56 / 0.20 / 0.06 | 1.00 / 0.68 / 0.68 / 0.25 / 0.08 |
- **確実**: 建設の方針ダイヤル `railBuild` は、方針に関係なく 1840→1900年に 1.0→0.06 に下がる（1800年開始ゲームの100年の経済循環: 1850〜79年が停滞、1880〜99年が不況）。`planRailGen` は `railBuild < 0.05` で何も計画せず、新設の同時数は `1 + round(railBuild×2)` なので、1890年代以降はどの方針でも新設が細る。これが「1860年以降の停滞」の主因の一つ。
- **確実**: 鉄道重視は、その前の1840〜1860年の建設が均衡より少ない（開通済み 26 対 52）。方針の差が逆向きに出ている。
- **未特定**: 鉄道重視で1840〜1860年の建設が少ない理由。候補生成の `svc` の判定（道路の代替度 `competeWeight`）・予算の配分（`roadShare` 0.26）・方針ダイヤルが1950年以前は1950年の値で平ら（`eras.ts` の PROFILE のキーフレームが1950年から）であること。次の手順は、1840〜1860年の年ごとに、候補の数・採用数・資金の残りを方針別に記録して比較すること。
- 提案: 方針ダイヤルを1800年開始用にも定義し（1950年以前を平らにしない）、経済循環の不況期でも「重視した輸送機関は最低限の建設枠を保つ」ようにする。ただし、無制限に建てさせない（人口・需要・地形・予算・技術の条件は維持）。これは長期のバランスを変えるので、測定を伴う独立の作業にする。

## B. 海路重視の技術解禁・発展（設計案、未実装）
- 現状: 船・港・渡船は1800年に既に実用で、技術の関門がない。海路重視は方針ダイヤル（`seaBias`）の予算効果だけ。
- 設計案（架空の未発明技術として扱わない）: 港湾・船舶の**能力の段階**を、関門ではなく「運用の等級」にする。例: 帆船→蒸気船（定期の蒸気船航路が開く年）、港湾の浚渫と岸壁の整備（港の取扱量の上限）、運河と内水の航路。海路重視は等級の上がる年を、鉄道・道路と同じ露出方式（実験10年・実用20年まで、露出に比例、単調）で早める。効果は渡船の速度・積載・就航の頻度と港の取扱量に出す。年表・地図帳へも同じ判定で出す。
- 実装が要るもの: 渡船・港の速度/容量の等級パラメータ（`ferry.ts`/`hubs.ts`）、年表の行、テスト。長期の輸送配分に影響するので、測定を伴う独立の作業にする。

## C. 元号・技術・時代循環の重複、完成済み施設の消滅（点検済み）
- 技術の関門は、露出が増えるだけの単調な判定なので、元号の変更で完成済みの施設は消えない（`s40.test.ts` が 1800〜2050 を走査）。
- 効果の重複: 重視方針の効果は（1）方針ダイヤル（予算）と（2）技術の関門の前倒し、の二層。1950年以前は（1）が平らなので重複は小さい。経済循環（`railBuild` の低下）は方針と独立に効く。重複を数値で整理するのは A と同じ測定が要る。

## D. Issue #60: 旧市町村の都市システムへの統合（未実装・設計案）
- 現状（実装済み）: 旧市町村の代表点に集落を段階的に成立させ（`oldmuni40.ts`）、人口で町・市へ昇格（名前と年表）。ただし「市」は集落の格付けで、シミュレーションされる都市（`w.cities`）ではない。
- 統合に必要なもの: (1) 市へ昇格した場所を `w.cities` に加える（`cityById`/`cityByCell` などの索引、`sim.cities` の状態、府県ごとの候補の零和 `city17`・容量 `cap20`・`potential17` の重み）。(2) 世界はセーブから再構築されるので、追加した都市の定義を `sim` に保存し、読込時（`attachPendingSim`）に世界へ復元する移行。(3) 都市ID（例 `O-<標準地域コード>`）が旧セーブと衝突しないこと。(4) 都市数の増加が `an.T`（都市数の二乗）などの計算量に与える影響の測定と上限。(5) 1950年開始・旧セーブに影響しないこと。
- 危険: `w.cities` は全体の索引・描画・台帳・人口配分が前提にする固定リスト。途中で増やすには、各所の前提の確認が要る。**別Issue・別PRで、測定と保存互換のテストを先に書いてから**行う。

## D の基礎測定（Issue #67、実施済みだが判断材料にならない）と、未実装の明記
- 目的: 都市数を増やしたときの需要の分析（`analyze`、都市数の二乗の行列）の時間を知る。
- 方法: 1800年開始・固定シード7の世界（都市 61）に、合成の都市を 0/50/100/200/400 加えて `analyze` の時間を測った。
- 結果: 23 / 5 / 6 / 8 / 16 ms（都市 61〜461）。**都市数に対してほぼ平坦**に見えるが、合成の都市は道路網（ノード）につながっていないため、分析が実質的に無視している。したがって**実際の統合後の計算量を表さない**。

- 次の手順: (1) 昇格都市の定義の保存と復元だけを先に実装し、旧セーブ・1950開始に無影響なことをテストする（まだ都市は増やさない）。(2) 1都市ずつ道路につないだ状態で `analyze`・計画の時間を測る。(3) 上限（例: 活動する昇格都市 数十）を測定から決める。
