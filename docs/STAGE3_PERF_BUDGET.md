# Stage 3 性能予算と段階移行計画（Issue #8）

Pixel 7a / Android Chrome を基準に、CPU×6の計測（`tests/e2e/perf.spec.ts`）で守る。

## 予算
- 主スレッドの連続タスク: **≤ 300ms**（CPU×6計測。実機では約半分）。生成・シミュレーション・描画更新はすべてスライス実行。
- 1フレームのシミュレーション時間: ≤ 8ms。遅れたら時計を落とす（要求の滞留は上限つき）。
- JSヒープ: 通常運転で **≤ 250MB**、長時間実行で増え続けないこと（GC後一定）。描画オブジェクトは生成し直さず再利用。
- 起動時に読み込むデータ（圧縮前）: 地形標高0.15MB + 地理データ0.03MB + 交通網 **≤ 3MB**。大きいものは遅延読み込み。
- 保存: 1回 ≤ 1MB・≤ 80ms。月の境界でのみ。履歴・イベント・スナップショットは上限つき。
- 描画: 交通網レイヤーの再描画 ≤ 2Hz。縮尺で詳細度を落とす（ズームアウトでは主要路線のみ）。

## 段階移行
1. Issue #7: 安定化（完了。`docs/STAGE3_ISSUE7_FREEZE.md`）。
2. 実地形・実路線データの調達と利用条件の確認、地形の手動変形を凍結して実際の日本の地図から開始。
3. 道路・鉄道の共通ネットワークと1950年風の初期網、需要配分とモード競争の最小縦断。
4. 三世界線・情勢イベント・10年ごとの政策介入。
5. 年代比較・路線台帳・未成線/廃線・保存拡張。
既存のStage 1/2のコードとセーブは参考実装として残し、新旧のセーブは別キーで分離する。

## Stage 3 の実測（CPU×6 の Chromium、ソフトウェアGL。`tests/e2e/perf3.spec.ts`、PERF=1）
実機（Pixel 7a）ではなく、デスクトップのChromiumをCPU6倍遅くしたもの。画面描画もCPUで行うため、実機のGPU描画より重い。

| 項目 | 結果 | 予算 | 判定 |
| --- | --- | --- | --- |
| 起動＋地形生成（Worker） | 3.2 秒 | — | 画面は固まらない |
| 開通の儀（1950年の道路+鉄道網を分割生成） | 8.5 秒（進捗表示つき、10ms単位に分割） | — | 分割済み |
| JSヒープ（GC後、×20を90秒運転） | 19MB → 79MB（年を重ねるほどデータが増える分） | ≤250MB | 達成 |
| パン・ズームを繰り返したあとのヒープ | **73MB**（修正前は131MB） | 一定 | 達成。原因は地図の背景レイヤーを作り直すたびに Graphics の描画情報（context）が解放されていなかったこと。`destroy({children:true, context:true})` で解決 |
| 100年運転後のセーブ | 約1.0〜1.2MB（機能追加で増加）、シリアライズ76ms | ≤1MB・≤80ms | 上限を少し超える。`compactSim`（古い計画の整理・小数の丸め）と年表の上限（1000件、日常的な出来事から捨てる）で抑制 |
| シミュレーションの1回の塊（`pump`） | 最大198ms（平均25ms） | ≤300ms | 達成 |
| 道路・鉄道レイヤーの再描画（JS側） | 最大124ms（平均43ms） | ≤2Hz | 達成 |
| 主スレッドの長いタスク（>50ms） | ×20運転中の最大 **718ms**（ソフトウェアGLの描画を含む） | ≤300ms | **未達（この計測環境では）**。GPU描画のある実機では軽くなるはずだが未確認。縮尺が小さいときは鉄道の枕木（白い点線）を描かない、帯を細くする、などで描画負荷を減らした |

### 見つかって直したこと
- 保存（`persist`）が「時計が忙しいうちは待つ」だけだったため、×20では保存されず、待ちタイマーが積み重なっていた。30秒待っても空かなければ、進行中の月を終わらせて保存する。待ちタイマーは常に1本。
- 旧Stage 2のバイパス完成処理が、旧道が途中で分割されたあとに路線を壊すバグ（鉄道の追加で起きやすくなった）。
