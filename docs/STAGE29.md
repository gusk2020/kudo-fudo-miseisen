# Stage 29

## A 遷都の年・停止・旧セーブ
- 実機で 2100 年を通過して 2200 年になった原因: ゲームが**旧仕様のセーブ(Stage 27 以前に始めたゲーム)の続き**だった可能性が高い。Stage 28 は新規ゲームにだけ `relocFirst=2100` を付け、旧セーブ(この印がない)は 2200 起点のまま扱う設計で、ブラウザの保存領域(IndexedDB)は Stage ごとのページ間で共有されるため、Stage 28 を開くと Stage 27 の自動保存が自動で再開されうる。新規ゲームの作成経路は1か所(`createSimGen`)で、そこで必ず `relocFirst: 2100` と `relocOrigin: "new"` が付く(E2Eで確認)。
- 診断: メニューの先頭に「遷都: 次は○○年(起点○○年・新しいゲーム/旧ゲームから2100年起点へ移行済み/旧ゲーム(2200年起点を維持))」を表示する(`relocDiag`)。
- 旧セーブの移行(`adoptRelocSchedule`、読込時): **2100年未満で、遷都のイベントも履歴もない旧ゲーム**だけを 2100 起点へ移す(過去は何も起きていないので履歴は書き換わらない)。2100 年を過ぎている旧ゲーム、遷都の履歴がある旧ゲームは従来の 2200・2350… のまま(過去のイベントを後から出さない・二重に出さない)。
- 停止: `auto`/`priority`/`idleAuto`(完全自動・半自動・手動寄り)× ×1/×20 のE2E(2098 年から自然に進めて 2100 年ちょうどに開き、選択完了まで時計が動かない→選択→遷都直後の保存→2248 年から 2250 年に停止)。
## B 自動セーブ・復元
- 2050 年のセーブポイントを 2079 年で読み込むと戻らなかった**原因**: 読込のあと、**セーブからの実時間(放置分)を取り戻す「放置時間のキャッチアップ」が読み込んだゲームにも走り、最大30年分(上限360か月)を一気に進めていた**(2050+29〜30 年 ≒ 2079〜2080 年)。復元そのものは正しく、そのあとで先へ進められていた。E2Eで「保存から1時間後」を再現し、修正前は失敗、修正後は通ることを確認した。
- 修正: プレイヤーが操作する読込(セーブポイント・番号スロット)は保存された状態そのもので始め、放置時間は進めない(ページを開き直したときの自動再開のキャッチアップは従来どおり)。
- 遷都直後のセーブポイントが作られなかった原因: 作成のきっかけが「時計が次の年の頭を始めるとき」だけで、遷都の選択を終えても時計が止まったまま(時間停止・速度0)だと作られなかった。選択完了(今のまま・国道0号の開通・見送り)の**その場**で作る。
- 書込の確認: 書いたデータを読み戻してサイズと一覧への登録を確認してから成功とする(失われる記憶域では失敗として通知し、以前の一覧は変えない)。単体テスト済み。
- E2E: 2050 を作成→2079 へ→保存の1時間後に 2050 を読込→年・月・辺数が保存どおり→進行→番号スロットへ保存→再読込→読込→遷都は二重に起きない。
## C 水域描画
- 四角い海色の境界の**原因**: Stage 28 で作った「海の層」が、輪郭の外にはみ出る陸のセルを一色(浅い海色)で塗っていたため、深さで濃淡のついた隣の海セルと四角い段差になった。陸のセルは最も近い海セルの色で塗る(数セル分の広がり)ように修正。
- 琵琶湖周りのにじみの**原因**: 格子の湖セルが青く塗られ、補間で周囲の陸ににじんでいた。陸の層では湖セルも普通の地面として塗り、湖は輪郭から描く。
- 河川: 5km刻みの断片をつなげてなめらかな線に(位置は動かさない・どこにもつながらない断片は従来どおり描かない)、海岸ポリゴンで切り抜いて海の中へはみ出さない。川の色は海より明るい青にして河口で海に溶ける。
- 湖: `tools/build_lakes.py`(OpenStreetMap・GitHub Actions で実行)が主要な湖・汽水湖と湖中島を `src/data/lakes.json` に書き出す。表示専用で、シミュレーション・地形・保存には影響しない。水の色(海・湖・汽水湖・川・湖岸)は `src/render/water.ts` の共通定義。
## D 凡例背景
- 縦型凡例の背景を道路地図の土地と同じ色(`ROAD_LAND = 0xf3efe4`、地図の塗りと同じ定数)に。文字は濃い色、ボタンも明るい配色。点線・破線は復活していない。
## E 復興
- Stage 28 の復興(周期・人口・建設・復旧)は変更していない。

## F ×20性能
測定環境: ヘッドレス Chromium(ソフトウェアGL)+CPU 6倍遅延、node のCPUプロファイル。**Pixel 7a 実機・Android Chrome の GPU とは異なり、実機の速度は保証しない**。
- 分離計測(node、2100〜2130 年、包含時間): 年次処理 73%(需要解析 25%・休止道路の孤立判定 8%・建設計画 9%・人口更新 5%)、月次処理 16%、GC 6%、描画・保存は別(ブラウザ側で計測)。復興期の建設件数の増加は1年あたり 250〜280ms のコストで、復興期・平衡期・衰退期でほぼ同じだった。
- 追加の改善(結果は同一、2100 年時点の状態ハッシュ・辺数・集落数・イベント数・乱数状態が完全一致): 休止道路の孤立判定で道路グラフと成分計算を共有・別の迂回路がある道は早期終了(Stage 28 の分と合わせて 2100〜2130 年の計算 7.5 秒→7.1 秒、Stage 28 の改善前から通算で約 2割減)。
- ブラウザの×20(40秒間に進む月数、同条件・各2回、Stage 28 / Stage 29): 1960: 89・91 / 78・72、2050: 64・59 / 49・59、2110: 72・72 / 72・69、2160: 95・92 / 94・83、2210: 95・83 / 95・83、2260: 119・120 / 118・108。**差は測定の揺らぎ(±15%)の範囲で、ブラウザ上の速度改善は実証できていない**(計算の短縮分は、描画・UI 更新・ソフトウェアGLが支配する環境では現れにくい)。1960〜2050 年で Stage 29 がやや低い値だが、描画時間(renderRoads の平均)は同水準(45〜74ms)。
- タッチ応答(ドラッグ中の入力から次のフレームまで、6倍遅延・ソフトウェアGL): 中央値 70〜470ms、p90 約 500〜650ms で、Stage 28 と Stage 29 に有意な差はない(揺らぎが大きい)。
- 保存: 直列化(JSON.stringify)は 120〜160ms(6倍遅延、実環境で約 20〜25ms)、gzip は 700〜870ms(6倍遅延、非同期のため入力は止めない)、約 215KB(1960 年)→ 392KB(2260 年)に圧縮。
- ×50 は復活させていない。計算の省略・年飛ばし・復興や人口の弱体化による見せかけの高速化はしていない。
