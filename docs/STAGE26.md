## B 府県境界が二重だった原因と修正
- **原因**: 地図に府県境が**2種類**、別のデータから描かれていた。
  1. 紫の階段状: `terrain.ts` が1セル5kmの格子に府県を割り当て、隣のセルと府県が違う辺を並べたもの(`t.borders`)。シミュレーション内部の割当用。
  2. 細い線: 海岸線 `coast-gmj.json`(地球地図日本。dataofjapan/land の**府県ごとのポリゴン**)を、ポリゴンごとに輪郭線として描いたもの。ポリゴンは府県単位なので、陸の内側の府県境も「海岸線」として描かれていた(しかも隣り合う2府県で2回)。
  実在の境界は後者、前者は格子による近似なので、位置が食い違い二重に見えた。
- **修正**: `src/render/gmBorders.ts`。2つのポリゴンが共有する線分=府県境、1つだけの線分=海岸と分け、実在の府県境を**1回だけ**、境界の色で描く。格子の階段状の境界は、実データに境界がない**北海道の3区分(HK-SAP/HAK/NEM)の内側だけ**に残す(49区分の表示を保つため)。
- 変えていないもの: 格子の府県割当(`pref`)・地形ハッシュ・人口割当・発展順位・選択。**シミュレーションは1行も変えていない**(表示のみ)。
- 確認: 熊本付近を拡大して前後をスクリーンショットで比較(二重線が1本に)。単体テストでポリゴンの分割(実データで境界>500・海岸>5000線分)、格子境界の絞り込み、E2Eで描画オブジェクトを確認。

## C 宮崎〜大分付近の青線
実機画像そのものは未入手のため、**同じ海域に青く見えうる描画を3種類すべて特定**した(コードと確認方法):
1. **外洋フェリー航路**(`roads.ts` の ferry 描画、青緑の破線・太さ3)。ゲームを2010年まで進めて `sim.edges` を調べると、宮崎市・大分市から大阪・広島・東京・岡山・神戸・姫路・松山・山口へ向かう外洋航路が**17本**あり、ほぼ全部が利用者0(`through=0`)のまま「供用中」。同じ日向灘沿いに何本も重なって見える。これは必要な交通線(Stage 22の外洋航路)なので消さず、**利用者のいない外洋航路は縮尺0.8以上でだけ描く**(利用の多い航路は従来どおり常に表示)。凡例の「海路(国内) 青緑の破線」と同じ定義。
2. **河川の断片**(`renderer.ts` の `drawHydro`、青・細い実線)。DEMの流路が宮崎市の北の海岸に**10kmの2区間だけ**あり、どこにもつながらない(全国の流路25本のうち5・10・12・27kmの4本がこの種の断片)。`src/render/streams.ts` で、つながった流路の全長が30km未満のものは描かない(データは変えない)。
3. **空路**(以前は白の薄い線が道路の下)。Stage 26 で黒の鎖線+白の下線に変更し、道路・鉄道の上に描く(D参照)。

## D 配色・凡例
- 道路・鉄道の**劣化(良/可/悪/荒廃)は地図の色を変えない**(内部の品質値は従来どおり計算・保存)。通常凡例の「傷み具合」の段も削除。`edgeStyle()` は品質を見ずに同じ見た目を返す(テストで全品質を確認)。
- 凡例の「新幹線」と「リニア」を **1項目「新幹線・リニア」**(青と紫の2本)に統合。内部の種別(`hsr`/`maglev`)・台帳・建設・シミュレーションは別のまま。
- 空路: 黒の「長・短」鎖線(10,4,2,4)の下に白の太い下線。道路(実線)・海路(青緑の破線)・廃線(灰の破線/点線)と線種・色で区別。以前は描画条件が縮尺0.3以上・軽量表示OFFだけで、全国表示(縮尺約0.2〜0.3)では出なかったため、縮尺0.12以上・軽量表示でも上位8本に。凡例に同じサンプル。
- 線の色: 種別ごと6色+黒・白・灰+強調1色。時系列比較(Eで廃止)の2色も消えた。

## E 過去履歴の廃止と自動セーブポイント
- **廃止**: 年代スライダー、過去の年の閲覧、時系列比較、連続スナップショット(5年ごと・最大80件、2310年で約0.46MB)。旧セーブの `snaps` は読込時に捨てる。台帳・年表・路線の番号履歴・各道路の履歴・イベント記録は残す。
- **自動セーブポイント**: 50年ごと(2000年〜、その年の最初の年境界)と、150年ごとの遷都イベントの**直前**(2200・2350・…)。2200のように50年と同時なら1件だけ。時計はその年境界で止まり、書き終えてから進む(`SimRunner.gate`)。保存するのは通常のセーブそのもの(地図・全シミュレーション・乱数状態・イベント状態・元号と遷都の履歴・首都ほか)なので、読み込むと元の続きになる(単体テストで、保存→読込した2つを同じ月数進めると全状態が一致することを確認)。
- 保存先: IndexedDB の `s3:cp:<年>:<50y|reloc>` と索引 `s3:cp:index`。**①〜⑤のスロットや自動保存(`s3:auto`)とは別のキー**で、書くのも消すのもこの接頭辞だけ。gzip圧縮(CompressionStreamが無ければ無圧縮)。
- **保持ルール(安全な初期値)**: **最大8件、合計48MB**まで。超えたら「50年ごと」の古いものから、次に「遷都直前」の古いものを消す。最新の1件は消さない。ユーザーのスロットは一切消さない。
- 失敗時: 書き込みは新しい本体→索引→古い削除の順。途中で失敗しても前のものは一覧・読込できる。索引が読めないときは索引を作り直さず中止(推測で上書きしない)。失敗は「自動セーブポイントを作れませんでした(理由)。ゲームはこのまま続けられます」と通知し、進行は止めない。
- UI: 保存メニューの①〜⑤の下に「自動セーブポイント」。1行=「2200年 遷都の直前(第1回) / 首都 / 副首都 / 容量」+読込(確認あり)。
- 実装中に見つけた不具合: **同じ地図のセーブを読み込んでもゲームが付かない**(`adopt` は地形の再生成の完了を待ってゲームを付けるが、地形が同じだと再生成が起きない)。スロットでも起きうる既存の不具合だった。読込後に地形があればすぐ付けるよう修正。もう1つ、保存メニューの組み立てが非同期で2回走ると行が重複する(3重になった)のを、最新の1回だけ表示するよう修正。
- 注: 指示書の「青・緑・橙の3色セーブスロット」は、コード上は**①〜⑤の5つの番号スロット**(色分けはない)。それらと自動保存(`s3:auto`、毎回の自動保存)は変えていない。
